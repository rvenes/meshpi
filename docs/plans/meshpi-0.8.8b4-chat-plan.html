Chatkopiering og meldingshistorikk i 0.8.8b4

Ei avgrensa TUI-forbetring som gjer chatloggen lett å kopiere frå og gir skall-liknande historikk med pil opp og ned. Planen bevarer radio-, database- og IPC-grensene frå 0.8.8b3 og legg b4 inn i den pågåande betatesten etter full signatur- og kvalitetskontroll.

1. Mål, omfang og ufråvikelege grenser

Brukarmål

Markere tekst i chatloggen og få han på utklippstavla utan å forlate TUI-en.

Skriveflyt

Hente fram tidlegare eigne meldingar med ↑/↓, som i eit skall.

Releaseform

Ny intern PEP 440-beta 0.8.8b4, ikkje endring av stabilkanalen.

Offentlege grensesnitt: Ingen endring i IPC-protokoll, databaseformat, CLI-kommandosyntaks eller radio-/kanalruting. Det nye brukargrensesnittet er avgrensa til tastane ↑/↓ når meldingsfeltet har fokus, og automatisk kopiering frå chatloggen.
  • Berre daemonen eig framleis SQLite-fila og Meshtastic-sambandet.
  • Ingen konfigurasjon på ein Meshtastic-node skal lesast for endring eller skrivast.
  • Ingen avhengigheiter skal leggjast til, og plattformlåsene skal derfor ikkje regenererast.
  • Database, profilar, historikk, aktiv gateway og driftsmodus skal bevarast gjennom oppdateringa.
  • Betaendringar skal aldri endre eller erstatte stabilmanifestet for 0.8.7.

2. Endeleg TUI-spesifikasjon

Meldingshistorikk per public-/DM-samtale

  • Når meldingsfeltet har fokus, går ↑ bakover gjennom eigne meldingar i den aktive samtalen.
  • ↓ går mot nyare oppføringar. Etter den nyaste oppføringa blir utkastet som stod i feltet før første ↑, gjenoppretta nøyaktig.
  • Historikken er separat for kvar public-kanal og kvar DM-samtale. Meldingar skal aldri blandast mellom samtalar eller lokale nodeområde.
  • Berre rader med utgåande retning skal takast med. Innkomande meldingar, traceroute-rammer, systemmeldingar og oppdateringsvarsel skal ikkje bli historikk.
  • Ved opning eller byte av samtale blir historia fylt frå dei siste 300 innlasta samtaleradene, i kronologisk rekkjefølgje.
  • Ei validert innsending blir lagd til i økthistoria straks. Ho skal dermed kunne hentast fram igjen også dersom den asynkrone sendinga feilar.
  • Etter omstart blir historia bygd opp att frå faktisk lagra utgåande meldingar. Ein sendefeil som aldri blei lagra, lever berre i den aktuelle TUI-økta.
  • Når historia er tom, skal ↑/↓ ikkje endre teksten. Etter henting står markøren ved slutten av teksten.
  • Piltastar i samtale-, node- og dialoglister skal fungere som før når meldingsfeltet ikkje har fokus.

Automatisk kopiering frå chatloggen

  • Venstre musedrag markerer framleis tekst i den valde chatloggen.
  • Når museknappen blir sleppt og markeringa er ikkje-tom, blir den markerte chatteksten kopiert automatisk.
  • TUI-en viser ei kort nynorsk stadfesting utan å leggje tekst i meldingsfeltet eller sende noko.
  • Ctrl+C skal framleis kopiere gjeldande markering.
  • Eit vanleg klikk eller ei tom markering skal ikkje overskrive eksisterande utklippstavleinnhald.
  • Kopiering bruker Textual si OSC52-baserte terminalutklippstavle. Terminalen må godta OSC52; macOS Terminal er ei kjend avgrensing.
  • Terminalen si eiga native markering, vanlegvis Shift + musedrag og terminalen sin kopieringskommando, blir dokumentert som reserveveg.
Sikker sendeflyt: Å bla i eller kopiere historikk skal aldri utløyse Enter, fylle inn ein mottakar, byte kanal eller sende ei melding automatisk.

3. Implementasjonsavgrensing og kvalitetsportar

Minste samanhengande kodeendring

  • Lag eit internt meldingsfelt som utvidar Textual Input med samtalespesifikk historikk, indeks og lagra utkast.
  • Aktiver rett historikk straks ved samtalebyte, og oppdater henne frå den ferdig innlasta samtalen utan å endre gjeldande utkast.
  • Handter Textual-hendinga for avslutta tekstmarkering berre når chatloggen har ei ikkje-tom markering.
  • Oppdater nynorsk TUI-hjelp, tastelinje, README og utviklingshistorikk.

Bandit-opprydding som releaseport

Baselinekontrollen fann seks medium B608-funn i den eksisterande b3-migreringskoden. Oppdatert prosjektinstruks krev at ingen medium eller høge funn blir ignorerte før release.

  • Erstatt dynamisk komponerte tabell- og spørjingsidentifikatorar med eksplisitte, tillatne SQL-variantar.
  • Ikkje demp funna globalt og ikkje svekk validering eller migreringsavstemming.
  • Bevar same rader, tabellar, transaksjonsgrenser og tapsfrie b3-migreringsåtferd.
  • Utvid migreringstestane slik at både trygt avgrensa og bevart legacy-innhald framleis blir avstemt.
  • To kjende låge subprocess-funn i releaseverktøyet kan stå att etter konkret vurdering; medium og høg skal vere null.
  • Alle målretta TUI- og migreringstestar grøne
  • python -m pytest -q grønt
  • python -m ruff check . grønt
  • Bandit utan medium/høge funn
  • git diff --check utan whitespacefeil
  • Ingen utilsikta avhengigheits- eller låseendring

4. Versjon, signering, Git og publiseringsgrenser

1Implementer og testAvgrensa b4-kode, dokumentasjon og Bandit-opprydding.
2Bygg og signerReint worktree, eksisterande låser og godkjend ekstern nøkkel.
3Commit og pushÉin avgrensa b4-commit på main, utan tagg eller GitHub Release.
4Stage og publiser betaBerre beta-treet etter rein global førehandsvising.

Versjonering og kjeldeintegritet

  • Auk pyproject.toml og meshpi/__init__.py frå 0.8.8b3 til 0.8.8b4, og oppdater eksplisitte testforventningar.
  • Oppdater betasida og utgåvenotata med chatkopiering, historikk og vidareført b3-dataversjon.
  • Bevar alle eksisterande brukarendringar. Stage berre b4-relaterte hunks og filer.
  • Bygg og signer frå eit reint mellombels Git-worktree basert på b4-committen, slik at urelaterte lokale endringar ikkje kjem inn i wheel-en.
  • Ta det genererte betamanifestet tilbake i same b4-commit før push.
  • Bruk commitmeldinga Release MeshPi 0.8.8b4 beta og push main. Ikkje lag tagg eller GitHub Release.

Signering og betapublisering

  • Kontroller den godkjende nøkkelpeikaren og ACL utan å lese eller skrive ut privat nøkkel eller sti.
  • Køyr releaseverktøyet med --channel beta og b4-utgåvenotat; ikkje handrediger hashar, storleikar, tid eller signatur.
  • Verifiser RSA-signaturen og faktisk SHA-256/storleik for wheel, tre låsefiler og tre installatørar.
  • Ta bytehash av stabilmanifestet før bygging og stadfest at det er uendra etter bygging, staging og publisering.
  • Bevar historiske beta-wheels og alle andre eksisterande stagingfiler.
  • Køyr den obligatoriske globale venes.org-førehandsvisinga. Stopp ved alle uventa endringar eller slettingar.
  • Publiser berre når førehandsvisinga er rein; verifiser offentleg betamanifest, betaside, wheel og alle sju manifestbundne artefaktar før installasjon.
Stoppregel: Feil signatur, hash, storleik, kanal, stabilbyte, Bandit-port eller uventa publiseringssletting blokkerer staging, publisering og installasjon. Det skal ikkje arbeidast rundt kontrollen.

5. Verifisert installasjonsomfang og rekkjefølgje

Målutvalet er basert på lesande kontrollar. Berre maskiner som faktisk køyrer 0.8.8b3, skal førast vidare til b4.

Maskin Verifisert tilstand B4-mål Planlagt rolle
rvelite MeshPi 0.8.8b3, Linux x86_64, always Ja · nr. 1 Første Linux-/SSH-installasjon og passiv TUI-smoketest
rvi9 MeshPi 0.8.8b3, Windows, always Ja · nr. 2 Windows-installasjon og lokal terminal-/utklippstavletest
rustdesk MeshPi 0.8.8b3, Linux arm64, always Ja · nr. 3 Produksjonsnær Raspberry Pi; berre MeshPi skal rørast
pi3 MeshPi 0.8.8b3, Linux arm64, always Ja · nr. 4 Produksjonsnær Raspberry Pi; HOOBS skal ikkje rørast
syncpi MeshPi 0.8.7, stabil kanal Nei Skal bli på stabil 0.8.7; Syncthing og andre tenester urørte
mac-rvmba Svarar, rett identitet og arm64; MeshPi er ikkje installert Nei Skal ikkje installerast, oppdaterast eller brukast som b4-mål

Kontrollert installasjonssekvens

  1. Før kvar maskin: stadfest identitet, versjon, driftsmodus, tenestestatus, aktiv versjonspeikar og doctor --offline.
  2. Installer først på rvelite med den offentleg verifiserte, signerte betakanalen.
  3. Når Linux-kontrollane er grøne, installer på lokale rvi9 og gjennomfør Windows-smoketest.
  4. Varsle før kvar MeshPi-tenesteomstart på rustdesk og pi3; installer sekvensielt, aldri parallelt.
  5. Etter kvar installasjon: stadfest 0.8.8b4, current/previous, same modus og profil, éin daemon, lokal IPC og rein offline doctor.
  6. Kontroller passivt at samtalehistorikk og eksisterande konfigurasjon framleis er tilgjengeleg. Ikkje opne eller logg privat meldingsinnhald.
Andre tenester: RustDesk, Docker, HOOBS, Syncthing, LaunchAgent-jobbar og andre systemtenester skal ikkje stoppast, restartast, oppdaterast eller brukast som testområde. Mac-en og syncpi er eksplisitt ute.

6. Testplan, rollback og akseptansekriterium

Automatiske TUI-regresjonstestar

  • Musedrag i chatloggen etterfølgt av museslepp legg den eksakte markeringa i utklippstavla og viser stadfesting.
  • Tom markering endrar ikkje utklippstavla; Ctrl+C kopierer framleis ei aktiv markering.
  • Historikken inneheld berre utgåande meldingstekstar frå aktiv samtale og bevarer kronologisk rekkjefølgje.
  • ↑ går eldre, ↓ går nyare, og siste ↓ gjenopprettar nøyaktig utkast.
  • Public-kanalar og DM-ar held separate historikkar, også når ein DM viser samanslåtte eldre ruter.
  • Ei validert innsending kjem straks i økthistoria; ugyldig eller tom innsending gjer det ikkje.
  • Samtale- og nodepiltastar, sending, meldingsvalidering, update-varsel og arkivering fungerer som før.

Rollback før produksjonsnære oppdateringar

  • Bruk eit isolert, tenestefritt oppdateringsoppsett med b3 som gjeldande og b4 som kandidat.
  • Framkall kontrollert feil i helsesjekken etter versjonsbyte.
  • Stadfest at oppdateraren automatisk set current tilbake til b3, bevarer data/config og rapporterer feilen.
  • Køyr deretter vellukka b4-oppdatering i same isolerte oppsett og stadfest rett previous-peikar.
  • Produksjonsnære mål skal ikkje oppdaterast før begge scenarioa er grøne.

Passiv smoketest etter installasjon

  • På Windows: marker ein ufarlig, synleg tekstbit, stadfest automatisk kopiering ved innliming, og kontroller Ctrl+C.
  • Over SSH på rvelite: gjenta kopieringskontrollen i den aktuelle terminalen og stadfest OSC52-åtferda.
  • I ein public-samtale og ein eksisterande DM: bruk ↑/↓ til å kontrollere historikk og utkast, men trykk aldri Enter.
  • Tøm meldingsfeltet og avslutt TUI-en med tenesta vidare i same modus.
  • På rustdesk og pi3: avgrens kontrollen til versjon, teneste, IPC, doctor og passiv historikkvising.
Radiosikker akseptanse: Smoketesten skal ikkje sende ei ekte melding – korkje public eller DM. Ingen automatisk test skal opne eit Meshtastic-samband. Ekte DM krev ei ny, separat bestilling og stadfesta full mottakar-ID og er ikkje del av denne planen.

Ferdigkriterium for b4

  • Historikk og utkast fungerer per samtale
  • Markering blir automatisk kopiert
  • Ctrl+C og terminalreserveveg er dokumenterte
  • Full testsuite, Ruff og Bandit er grøne
  • Rollback er bevist isolert
  • Stabilmanifestet er byteuendra
  • Sju beta-artefaktar er offentleg verifiserte
  • Fire stadfesta beta-maskiner køyrer b4 reint
  • syncpi står framleis på stabil 0.8.7
  • Mac-en er urørt og utan MeshPi-installasjon
  • Ingen radio- eller nodekonfigurasjon er endra
  • Ingen public- eller DM-testmelding er send
