Plan for 0.8.8b3

Ei avgrensa hardingsutgåve som gjer datamigreringa tapsfri, får daemonen trygt tilbake etter suspend/resume og etablerer eit målbart grunnlag for ein 7–14 dagars test før 0.9.0b1.

Stabil: 0.8.7 No i test: 0.8.8b2 Neste port: 0.8.8b3
Avgjerd

Lag b3 før den formelle langtidstesten

0.8.8b2 kan halde fram med å samle data medan b3 blir laga, men b2 skal ikkje vere utgåva som godkjenner 0.9.0. Den noverande schema-4-migreringa kan fjerne historikk som ikkje kan knytast eintydig til ein lokal gateway.

01 · Omfang

Kva som høyrer til i beta 3

Må med

Dataintegritet

  • Tapsfri migrering frå schema 3 til nytt schema.
  • Eksplisitt bevaring av uavklart legacy-historikk.
  • Radrekneskap og transaksjonell rollback.
  • Test mot realistiske, anonymiserte datasett.
Må med

Livssyklus

  • Oppdage at operativsystemet har vore suspendert.
  • Serialisert reconnect utan parallelt radiosamband.
  • Synleg reconnect-årsak i status og logg.
  • Automatiske og kontrollerte live-testar.
Kan vente

Ikkje b3-kritisk

  • Tidsfilter og synleg sideinndeling i TUI.
  • Fleire samtidige gatewayar.
  • Generelt importformat for databaseeksport.
  • Full BLE-støtte i Docker.

Trygg opprydding av gamle release-miljø, lengre reconnect-backoff og loggrotasjon er gode tillegg dersom dei kan gjerast utan å auke risikoen for hovudmåla. Dei skal ikkje forseinke dataintegritetsrettinga.

02 · Evidens

Kva 0.8.8b2 avdekte

Før oppgradering blei det teke komplette, tilgangsverna eksportar. Samanlikning av tabelltal før og etter schema-4-migrering viste at telemetri og posisjonar heldt fram med å vekse, medan eldre uskopte radtypar kunne bli fjerna frå den aktive databasen.

Testrolle Nodeoppføringar Meldingar Nodehandlingar Arkivmarkeringar Observasjonar
macOS / seriell −71 −3 −24 0 heldt fram å vekse
Linux / Pi 4 / seriell −13 −51 0 −4 heldt fram å vekse
Linux / Pi 3 / TCP −4 −27 0 −4 heldt fram å vekse
Ubuntu / seriell −7 0 netto −13 0 heldt fram å vekse

Dette er ikkje teikn på SQLite-korrupsjon. Det er konsekvensen av ein migreringsstrategi som prioriterer dataskilje ved å slette rader som ikkje kan tilordnast sikkert. For ei stabil utgiving skal uvisse gi read-only legacy, aldri stille sletting.

03 · Invariant

Reglar løysinga ikkje får bryte

Data og eigarskap

  • Berre daemonen eig SQLite-fila og radiosambandet.
  • Profiler er transportspor; lokal node-ID er dataeigar.
  • Uavklarte rader er lesbare, men aldri sendbare.
  • Eksisterande database, profilar og innstillingar blir bevarte.

Radio og tryggleik

  • Ingen node-, kanal- eller radiokonfigurasjon blir endra.
  • Automatiske testar bruker mock og sender ingenting.
  • Live-testen er passiv; public og DM er utanfor planen.
  • IPC held seg på loopback eller privat Unix-socket.

04 · Arbeidsstraum A

Tapsfri schema-migrering

B3 bør innføre eit nytt, versjonert schema og migrere i éin eksplisitt transaksjon. Uavklarte kjelder blir bevarte i ei eiga tabell, til dømes legacy_unscoped_records, med kjeldetabell, kjeldenøkkel, årsak, tidsstempel og original rad som strukturert JSON.

1. Tel Ta radtal og identitetsoversikt før noko blir endra.
2. Tilordne Bruk meldingobservasjon, gateway-ID, profilspor og DM-retning.
3. Bevar Flytt alt tvitydig til leseorientert legacy-lager.
4. Avstem Kvar kjelderad må ha nøyaktig éin dokumentert destinasjon.
5. Commit Byt schema berre når avstemming og integritet er grøn.

Tilordningsrekkjefølgje

  1. Bruk ein eintydig lokal node-ID frå message_observations, utgåande avsendar eller innkomande DM-mottakar.
  2. For telemetri og posisjon: bruk gyldig gateway-node, og deretter profilens sist kjende lokale node-ID.
  3. For nodeoppføringar: opprett skopierte rader for kjende lokale område som faktisk har observert noden; ikkje slett originalen før avstemming.
  4. For traceroute og andre nodehandlingar: bruk knytt utgåande pakke. Dersom det ikkje finst ei eintydig kopling, bevar rada som legacy.
  5. Arkiveringsstatus blir flytta berre når samtaleruta kan tolkast. Resten blir bevart med årsak, ikkje forkasta.

Avstemming

skopierte + legacy = kjelderader for kvar tabell. Avvik skal avbryte transaksjonen og la den gamle databasen stå urørt.

Idempotens

Andre oppstart etter vellukka migrering skal gjere null endringar. Eit simulert avbrot midt i migrering skal rulle heilt tilbake.

05 · Arbeidsstraum B

Plan for maskiner som alt har køyrt b2

Dei verna før-eksportane inneheld dei fjerna radene. B3 må skilje mellom å rette migreringa for framtidige oppgraderingar og å hente tilbake data på dei fire testmaskinene som alt er migrerte.

Påkravd

Isolert rekonstruksjonstest

  • Les berre skjema, radtypar og anonymiserte felt frå eksportane.
  • Bygg testdatabasar utan meldingstekst eller posisjonsverdiar.
  • Køyr ny migrering og samanlikn tabell-for-tabell.
  • Rå eksportar skal aldri inn i Git, bygg eller planarkiv.
Separat godkjenning

Faktisk recovery

  • Lag først ein tørrkøyring som berre rapporterer planlagde endringar.
  • Importer aldri over eksisterande rader eller sendbare ruter.
  • Uavklarte postar går til legacy-lageret.
  • Køyring mot live-data krev ny eksport og uttrykkeleg godkjenning.

Recovery-verktøyet skal gå gjennom daemon-/vedlikehaldsflyten og respektere at berre éin prosess eig databasen. B3 kan publiserast når den tapsfrie migreringa er bevist; sjølve innflettinga av dei private før-eksportane er ei eiga, kontrollert driftsoppgåve.

06 · Arbeidsstraum C

Reconnect etter suspend og stille sambandsbrot

Ubuntu-testen viste at operativsystemet kunne vere i djup suspend i fleire dagar. Etter oppvakning fanst seriellporten framleis, medan Meshtastic-lesaren ikkje leverte nye hendingar og status blei ståande på «tilkopla». Ein kontrollert MeshPi-restart opna sambandet og gav fersk telemetri straks.

Oppdaging

Sammenlikn veggklokke og monoton klokke for å oppdage eit suspend/resume-gap. Kontroller òg om transportlesaren faktisk lever.

Handling

Be den eksisterande, serialiserte reconnect-flyten lukke gammalt grensesnitt og opne same profil på nytt. Aldri to samband samtidig.

Synlegheit

Status og logg viser årsak, sist gyldige hending og tidspunkt for siste reconnect utan å logge privat meldingstekst.

  • Mocka test med falske klokker og suspend-gap.
  • Mocka test der transporttråden døyr utan vanleg disconnect-signal.
  • Test av backoff slik at feil ikkje gir tett reconnect- eller loggsløyfe.
  • Kontrollert live suspend-test berre når operatøren er til stades.
  • Automatisk dvale blir ståande avslått under den lange datatesten.

07 · Verifikasjon

Automatisk testmatrise

Område Påkravd test Bestått når
Migrering Schema 3 → nytt schema med scoped, tvitydig og ugyldig data. Alle kjelderader er skopierte eller ligg i legacy; null stille sletting.
Rollback Injiser feil etter kvar migreringsfase. Original schema og radtal er byte-for-byte logisk urørte.
Idempotens Køyr migrering og installatør to gonger. Andre køyring gir null datamodellendringar og frisk teneste.
Dataskilje To lokale nodar, delte og ulike profilar, public, DM og observasjonar. Ingen kryssvising; same lokale node deler framleis data.
Resume Falskt suspend-gap og stille transportlesar. Nøyaktig eitt reconnect-forsøk, ingen parallell radioeigar.
Yting Minst 35 000 telemetrirader og 4 000 posisjonar. 1 000-raders spørring under eitt sekund på svakaste Pi.
Tryggleik Full pytest, Ruff og Bandit. Alt grønt; ingen medium eller høge Bandit-funn.

Plattformtest før publisering

Windows og macOS

  • Oppdatering frå b2 via signert betakanal.
  • Aktiv/previous-peikar, autostart og offline doctor.
  • Mac: LaunchAgent-livssyklus og reconnect etter fråkopla USB.

Linux

  • Ubuntu x86_64, Raspberry Pi seriell og Raspberry Pi TCP.
  • Systemd-teneste, aktive profilar og private filrettar.
  • Ingen endring av andre produksjonstenester på Pi-ane.

08 · Bygg og release

Signert beta utan å røre stabilkanalen

  1. Oppdater versjon til 0.8.8b3 i kode og testar.
  2. Oppdater DEVELOPMENT.md med funn, designval og teststatus.
  3. Regenerer plattformlåser berre dersom ei avhengigheit faktisk er endra.
  4. Køyr full test, Ruff, Bandit og relevant skriptsyntaks.
  5. Bygg med betakanalen og tydelege utgåvenotat.
  6. Signer manifestet etter siste artefaktendring.
  7. Verifiser storleik og SHA-256 for wheel, tre låser og tre installatørar.
  8. Publiser berre under betaområdet; stabil 0.8.7 skal stå urørt.

09 · Utrulling

Canary først, éi maskin om gongen

Oppdateringane blir sekvensielle for å unngå belastning på nedlastingspunktet og for å stoppe tidleg dersom ein plattform finn ein feil. Kvar maskin får ein ny konsistent eksport før oppdatering.

Fase 1 · Lokal utvikling

Implementer og bevis migreringa

Mocka testar, anonymiserte fixtures, feilinjeksjon og full lokal test.

Fase 2 · Canary 24 timar

Windows, deretter Ubuntu-testmaskina

Kontroller dataskilje, ferske tidsstempel, CPU, RAM og service-livssyklus.

Fase 3 · Plattformbreidde

Mac, Pi 3 og Pi 4

Éi oppdatering om gongen; verifiser før neste maskin blir rørt.

Fase 4 · Soak 7–14 dagar

Passiv langtidslogging

Ingen radiosending. Følg radtal, duplikat, tidsstempel, yting og reconnect.

Fase 5 · Avgjerda

Opne arbeidet med 0.9.0b1

Berre når alle b3-portar er grøne og ingen migreringsavvik står att.

Avgrensing: Den fysisk fjerne produksjons-Pi-en blir ståande på stabil utgåve og er ikkje del av b3-utrullinga.

10 · Exit-kriterium

Godkjenningsportar før langtidstesten tel

G1

Radbevaring

Kvar kjelderad har ei skopiert eller legacy-destinasjon; avstemmingsrapporten har null avvik.

G2

Dataskilje

Nodeliste, meldingar, arkiv, telemetri, posisjon og handlingar er avgrensa til rett lokal node.

G3

Resume

Daemonen finn tilbake etter kontrollert suspend/resume utan omstart av maskina og utan parallelt samband.

G4

Ressursar

24-timars snitt under 3 % CPU på Pi, under 2 % på PC/Mac, RSS under 100 MB og ingen uavgrensa loggvekst.

G5

Oppdatering og rollback

Signert b2→b3-oppdatering er idempotent, bevarer profilar og database og held ein fungerande previous-peikar.

G6

Soak

7–14 dagar utan datatap, feil kjeldenode, fastlåst samband, vedvarande ressursauke eller nye tryggleiksfunn.

11 · Langtidstest

Kva som skal målast under b3-soaken

Dagleg

  • Versjon, tenestestatus og aktiv profil.
  • Siste telemetri- og posisjonstid.
  • Tal på nodar og observasjonar per lokal node.
  • Nye reconnect- eller databasefeil.

Kvar 2.–3. dag

  • CPU-tid, RSS og diskvekst.
  • Duplikatnøklar og sorteringsbrot.
  • Ugyldige eller urimeleg framtidige tidsstempel.
  • Spørjetid for 1 000 nyaste observasjonar.

Ved slutten

  • Ny komplett eksport med tabelltal.
  • Samanlikning mot startpunkt og forklaring på all vekst.
  • Plattformvis installasjons- og doctor-kontroll.
  • Avgjerd: 0.9.0b1 eller ny b3-retting.

12 · Stoppvilkår

Stopp utrullinga dersom

  • ein migrert eller legacy-rad manglar i avstemmingsrapporten;
  • aktiv lokal node eller profil endrar seg uventa;
  • tenesta opnar meir enn eitt radiosamband;
  • CPU ligg over 5 % eller RSS over 150 MB over tid utan forklaring;
  • databasen gir integritetsfeil, eller eksporten ikkje blir komplett;
  • oppdateringa påverkar andre tenester på ei produksjonsmaskin.

Ved stopp: ikkje slett eller nullstill data. Bevar logg og eksport, bruk previous-peikaren dersom det er trygt, og krev uttrykkeleg godkjenning før eventuell gjenoppretting av database.

13 · Leveransar

Det b3-arbeidet skal etterlate

  • Versjonert, tapsfri migrering med dokumentert legacy-modell.
  • Automatiske migrerings-, rollback-, idempotens- og resume-testar.
  • Avgrensa recovery-dry-run for b2-eksportar.
  • Oppdatert utviklingsstatus og utgåvenotat på nynorsk.
  • Signert b3-manifest og verifiserte artefaktar berre i betakanalen.
  • Canary-rapport og 7–14 dagars soak-rapport utan privat innhald.
  • Ei eksplisitt avgjerd om kva som går vidare til 0.9.0b1.
Denne planen er for det private MeshPi-testmiljøet. Han inneheld ingen passord, token, nøklar, private meldingar, koordinatar eller eksportdata.
